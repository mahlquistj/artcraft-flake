# artcraft-flake

> **Generated by AI.** This flake, its Nix expressions, scripts and
> documentation were written by `qwen3.8-flash` during a session (or several),
> including the commit messages. Everything here was built and run on
> `x86_64-linux`, but it has not been reviewed line by line by a human — treat it
> as a starting point and audit `pins.lock.json` / `pins.nix`, the pinned upstream
> releases and the derivations before trusting them with anything important.

A Nix flake for storytold's **Craft app suite** on Linux: PhotoCraft, LightCraft,
FilmCraft, SoundCraft, VectorCraft, PdfCraft, WordCraft, GridCraft, DeckCraft,
CADCraft, DesignCraft, EffectCraft — plus **ArtCraft** itself.

Two packaging strategies live side by side, because the upstreams differ:

| | how it is packaged | why |
|---|---|---|
| Craft apps (`photocraft`, …) | **prebuilt Linux tarball**, patched + wrapped | upstream ships signed-for-nada but complete `.tar.gz`/AppImage/deb/rpm/flatpak for x86_64, aarch64 and (tarball-only) riscv64, with the `.desktop`, icons, mime types and AppStream inside |
| **ArtCraft** | **source build** (`artcraft-native` crate) | its releases ship only macOS and Windows installers — nothing for Linux |

Metadata is data-driven: `products.nix` (identity, asset naming, runtime needs,
never a hash) + `pins.lock.json` (generated version/tag/url/sha256 per system,
rewritten by `nix run .#update` with **zero Nix builds**).

`PLAN.md` is the working design doc: what was measured, the phases (P0 and P1
done, P2 next) and the open decisions.

## Craft apps: try it

```bash
nix run .#photocraft                  # window opens (Wayland or XWayland)
nix build .#photocraft                # result/bin/photocraft + result/bin/photocraft-cli
result/bin/photocraft-cli --version   # headless CLI: convert|info|run|batch|droplet|commands|mcp
nix build .#craft-suite               # all twelve pinned apps in one symlink join (~3 GB)
nix run .#update -- --dry-run         # what would bump, no writes, no builds
nix flake check                       # eval test per arch, <app>-cli smoke tests,
                                      # desktop/metainfo validation, NixOS module check
nix build .#checks.x86_64-linux.nixos-crafts-module   # the module contract alone
```

All twelve apps are pinned and build: cadcraft, deckcraft, designcraft,
effectcraft, filmcraft, gridcraft, lightcraft, pdfcraft, photocraft, soundcraft,
vectorcraft, wordcraft (`craft-launcher` is metadata-only by decision, see
below). Adopting one that is not pinned yet is the same command:

```bash
nix run .#update -- <product>         # appends its pins; the package appears automatically
```

`tests/wrapper-audit.sh` is how the per-product wrapper flags get decided: for
every pinned product it prints the ELF `NEEDED` list, the sonames the binary
dlopens, and whether it references ALSA/PipeWire/ffmpeg/xdg-open. Run it after a
bump and re-read `products.nix` — that audit is what turned `needsAlsa` from a
guess into "deckcraft, effectcraft, filmcraft, soundcraft have
DT_NEEDED libasound.so.2, the rest do not" and removed `ffmpeg` everywhere (no
product references it).

## Craft apps: install it

**Modules** (`nixosModules.crafts` / `homeModules.crafts`) are generated from
`products.nix`, one option per product, plus a convenience list:

```nix
# configuration.nix
{
  inputs.craft.url = "github:YOU/artcraft-flake";   # or "git+file:///home/maj/projects/artcraft-flake"

  imports = [ craft.nixosModules.default ];   # = artcraft + crafts

  programs.photocraft.enable = true;
  programs.filmcraft.enable = true;

  # or the whole set at once; the list is a mkDefault, so an explicit
  # programs.<app>.enable = false still wins.
  programs.crafts.enable = [ "lightcraft" "vectorcraft" "gridcraft" ];

  # Menu integration comes from upstream's tarball and lives in the package's
  # `desktop` output. Turn it off per app to keep the binary + CLI only:
  programs.pdfcraft.enableDesktopEntry = false;

  # Every Craft app does file open/save and the colour picker through
  # xdg-desktop-portal; the module warns when this is off.
  xdg.portal = { enable = true; extraPortals = [ pkgs.xdg-desktop-portal-gtk ]; };
}
```

The same `programs.<app>.{enable,package,enableDesktopEntry}` and
`programs.crafts.enable` exist for home-manager via `homeModules.crafts`
(`homeModules.default` merges both modules).

**Overlay only**, if you would rather not use a module:

```nix
nixpkgs.overlays = [ craft.overlays.default ];
# Both outputs, because buildEnv links only the default output:
environment.systemPackages = [ pkgs.photocraft pkgs.photocraft.desktop ];
```

**Ad-hoc, no config:** `nix profile install path:.#photocraft`.

Upstream ships the desktop entry (`ai.storyteller.photocraft.desktop`), the
hicolor icon set + scalable SVG, mime types and AppStream metainfo inside the
tarball, so this flake authors **none** of those — they are validated, not
written: `pkgs/craft-app/tests.nix` runs `desktop-file-validate` and
`appstreamcli validate --no-net` over them and checks that the AppStream
`<release version>` equals the version in `pins.lock.json`. Both families are
flake checks (`checks.<system>.desktop-assets-<app>`).

## Craft apps: updating the pins

```bash
nix run .#update                       # every product already in pins.lock.json
nix run .#update -- photocraft filmcraft
nix run .#update -- --all              # every packageable product in products.nix
nix run .#update -- --dry-run           # print the pins diff only
nix run .#update -- --fail-on-change     # exit 1 if any pin would move (CI gate)
nix run .#update -- --verify photocraft   # then nix build .#photocraft
```

It resolves the latest tag (GitHub API, `releases.atom` fallback), downloads that
release's `SHA256SUMS.txt`, converts the base16 sha256 of each
`<app>-<ver>-linux-<arch>.tar.gz` with `nix hash convert`, and rewrites
`pins.lock.json` — no compilation, so bumping the whole suite costs one HTTP round
trip per product. A missing asset for a supported system is a **hard error** that
prints the tarballs the release did contain (upstream already renamed assets once:
`craft-launcher` ships `artcraft-launcher-*`). Downgrades are refused without
`--allow-downgrade`. The commit after a bump touches `pins.lock.json` only.

## Craft apps: what the builder does (and does not do)

`pkgs/craft-app/default.nix` is the single generic builder:

- `fetchurl` the pinned tarball (SRI hash from upstream's `SHA256SUMS.txt`).
- Copy `bin/` and `share/` verbatim into **two outputs**: `out` = `bin/*` plus
  `share/doc` (licences, OFL files, README), `desktop` = `share/{applications,
  icons, metainfo, mime}`. The split is what makes `enableDesktopEntry = false`
  mean something: both the NixOS system profile and home-manager's user
  environment link only the default output, so the modules install `desktop` as
  its own entry when it is wanted.
- `patchelf --set-interpreter` on each ELF (upstream hard-codes
  `/lib64/ld-linux-x86-64.so.2`, which on NixOS is nix-ld, not glibc).
- `makeWrapper` around every binary:
  - `LD_LIBRARY_PATH` = the sonames the app *dlopens* (photocraft checks them
    itself at startup: `libwayland-client.so.0`, `libxkbcommon.so.0`,
    `libxkbcommon-x11.so.0`, `libvulkan.so.1`, `libEGL.so.1`, `libX11.so.6`,
    `libX11-xcb.so.1`, `libxcb.so.1`, `libXcursor.so.1`, `libXi.so.6`) plus
    `libwayland-egl`, **libglvnd** dispatchers (`libGL.so.1`/`libEGL.so.1` —
    pdfcraft dlopens both), `libXrender`, `libdbus-1.so.3` (portal), fontconfig,
    freetype, alsa-lib for the four products that link it, and
    `/run/opengl-driver/lib` last so the system Vulkan ICD/GLX vendor wins.
    Never nixpkgs `mesa` — same bug as ArtCraft, see Troubleshooting.
  - `PATH` = `xdg-open`. The `needsFfmpeg` flag exists but is off everywhere: the
    binary audit found no ffmpeg/ffprobe reference in any Craft app (they carry
    their own codecs).
- `dontStrip`, `dontPatchELF`, `hardeningDisable = [ "all" ]`: the interpreter is
  the only byte we change in a 90 MB upstream binary.
- Asserts the product's glibc floor (2.35, 2.39 on riscv64) against nixpkgs'
  glibc and marks the package `broken` with a reason instead of failing eval.
- `meta.sourceProvenance = binaryNativeCode` — honest: these are upstream
  binaries, so they are not rebuildable from source and not nixpkgs-mainline
  material.
- `craft-launcher` is deliberately **not** packaged: it self-updates apps into
  `~/.local/share` and shells out to `flatpak`/`apt`/`dnf`/`zypper`, which
  conflicts with a Nix-managed install (see PLAN §5.3).

# ArtCraft (the source build)

ArtCraft itself is at https://github.com/storytold/artcraft: the AI creation IDE
the Craft apps are siblings of. This flake builds the `artcraft-native` crate,
i.e. the pure-Rust egui desktop client (no Tauri, no webview, no Node.js).

## Why build from source?

ArtCraft's GitHub releases only ship macOS and Windows binaries —
`ArtCraft_<ver>_universal.dmg`, `ArtCraft_universal.app.tar.gz`,
`ArtCraft_<ver>_x64-setup.exe`, `ArtCraft_<ver>_x64_en-US.msi` — and their CI
(`.github/workflows/artcraft-{macos,windows}-publish.yml`) publishes nothing for
Linux. There is no AppImage/deb/rpm/tar.xz to download, so a Linux package has
to compile the Rust workspace.

Two clients live in that workspace:

| Crate | What it is | Needs |
|---|---|---|
| `crates/desktop/artcraft` | the official Tauri app | Node 20+, npm, Nx, Vite, `cargo-tauri`, webkit2gtk |
| `artcraft-native` (**this flake**) | egui desktop app over the same API client crates | Rust + a few C libraries |

`artcraft-native` covers Create Image / Create Video / Create Audio, the feed,
library, lightbox, characters and sign-in. It is the practical way to get a
native ArtCraft binary on a NixOS desktop without a JavaScript toolchain.
Want the Tauri app instead? See "Packaging the Tauri app" below.

`artcraft-native` does not exist in any release tag (checked: `artcraft-v0.41.0`,
the newest at the time of writing), so `pins.nix` pins a commit on `main`.

## Checks and CI

`nix flake check` runs exactly what CI runs: `prebuilt-eval` (products vs pins
vs builder, across all three arches), twelve `smoke-<app>` headless loader tests,
twelve `desktop-assets-<app>` validations of upstream's files,
`nixos-crafts-module` (the generated module's install contract), the ArtCraft
build and `nixfmt`.

`.github/workflows/ci.yml` runs that on push to `main` and on every pull request
(the job is named **flake check**, and that name is what branch protection should
require).

`update-pins.yml` is the unattended bump path: Mondays 06:00 UTC it runs
`nix run .#update -- --all`, and if any pin moved it commits `pins.lock.json` to
the branch `craft/update-pins`, opens (or refreshes) a PR against `main`, and
enables **auto-merge with squash** — so the bump lands on its own once
`flake check` is green, and does not land if it is red. If nothing moved it
commits nothing and opens nothing. A later week where a previous bump PR is still
open force-pushes onto that same branch and comments the new diff, so there is one
current PR rather than a pile of competing ones (PLAN §6: stale pins were the
risk; silence was the failure mode).

### Setup the bump workflow needs

1. **Settings → General → Pull Requests**: allow squash merge and enable
   **Allow auto-merge**.
2. **Settings → Branches (or rulesets)**: protect `main` and require the status
   check **flake check**. Without a required check there is nothing for auto-merge
   to wait on, and a red bump could land immediately. Optionally require a review
   too — then a bot bump still needs one human click.
3. **Settings → Secrets and variables → Actions → repository secret**
   `CRAFT_BUMP_TOKEN`: a **fine-grained personal access token** scoped to this
   repository only, with *Contents: Read and write* and *Pull requests: Read and
   write*.

   Why a token at all: a PR opened with the default `GITHUB_TOKEN` gets its CI run
   in an *approval-required* state, so auto-merge would wait forever for a human
   click. Opening the PR as the PAT owner makes it a normal `pull_request` run.
   The token is used **only** for `gh` (PR authoring); the branch is still pushed
   with the job's own `GITHUB_TOKEN`, so the commit stays attributed to
   `github-actions[bot]`. When the PAT expires the job fails loudly at the first
   step with the reason, rather than quietly doing nothing.

`workflow_dispatch` on that workflow does the same thing on demand, which is the
way to test it once the secret exists.

## Install ArtCraft

**NixOS module** (`programs.artcraft.enable`):

```nix
{
  inputs = {
    nixpkgs.url = "github:NixOS/nixpkgs/nixpkgs-unstable";
    artcraft.url = "github:YOU/artcraft-flake";   # or "git+file:///home/maj/projects/artcraft-flake"
  };

  outputs = { nixpkgs, artcraft, ... }: {
    nixosConfigurations.desktop = nixpkgs.lib.nixosSystem {
      system = "x86_64-linux";
      modules = [
        ./configuration.nix
        artcraft.nixosModules.default     # = artcraft + crafts, as one module
        { programs.artcraft.enable = true; }
      ];
    };
  };
}
```

**home-manager module:**

```nix
{
  imports = [ artcraft.homeModules.default ];   # = artcraft + crafts
  programs.artcraft = {
    enable = true;
    desktopEntry = true;         # app-menu entry, default true
    # package = pkgs.artcraft;   # or your own derivation
  };
}
```

`programs.artcraft.enable` installs the package and a desktop entry. NixOS has no
`xdg.desktopEntries` option, so the NixOS module adds a `makeDesktopItem`
package to `environment.systemPackages`; the home-manager module uses
`xdg.desktopEntries`. The two APIs differ: `startupWMClass` is a
`makeDesktopItem` keyword but *not* a home-manager option (home-manager errors
with "The option … does not exist"), so on the home-manager side it is passed
through `settings.StartupWMClass`, which home-manager forwards to
`makeDesktopItem.extraConfig`.

Both sides are covered by eval-only harnesses (they do not build the app):

```bash
# NixOS module: package lands in systemPackages, desktop item is generated
nix eval --impure -f tests/nixos-eval.nix config.programs.artcraft.package.name

# home-manager module: merged option values, then the generated .desktop file
nix eval --impure -f tests/hm-module.nix options
OUT=$(nix build --impure --no-link --print-out-paths -f tests/hm-module.nix hmEntry)
cat "$OUT/share/applications/artcraft.desktop"
```

`tests/hm-module.nix` accepts `homeManager` and `artcraftFlake` arguments, so you
can point it at your own pinned home-manager revision instead of the default.

**Overlay**, if you just want `pkgs.artcraft`:

```nix
nixpkgs.overlays = [ artcraft.overlays.default ];
environment.systemPackages = [ pkgs.artcraft ];
```

**Ad-hoc, no config:**

```bash
nix profile install path:.#artcraft
```

## Updating ArtCraft's source pins

```bash
nix run .#update-pins                                     # HEAD of pins.branch
ARTCRAFT_REF=artcraft-v0.42.0 nix run .#update-pins       # a tag that has the crate
ARTCRAFT_REV=<full-sha> nix run .#update-pins             # an exact commit
ARTCRAFT_DATE=2026-11-01 nix run .#update-pins            # skip the GitHub API lookup
```

`update-pins` never hand-computes a hash. It writes a deliberately wrong hash
into `pins.nix`, runs `nix build .#artcraft`, scrapes Nix's `got: sha256-…` line
from the fixed-output mismatch, and repeats for `srcHash` then `cargoHash`.
Finally it builds once more with the real hashes and only exits 0 if that
succeeds — so a rev that fails to compile is reported rather than silently
pinned. `pins.nix` is regenerated from shell variables, so its comments and
layout stay stable across runs.

## What the ArtCraft derivation does

- `cargoBuildFlags = [ "--package" "artcraft_native" ]` — the workspace's
  `default-members` is the Tauri app, so the package must be selected explicitly.
- `installPhase` picks the binary out of `target/<triple>/release/` (the cargo
  build hook passes `--target`) and installs upstream's app icons
  (`crates/desktop/artcraft/icons/`) into `$out/share/{artcraft,icons/hicolor}`.
- `doCheck = false` — plain `cargo test` would try to build the Tauri crate and
  the frontend; run the Rust tests in `nix develop` with
  `cargo test --package artcraft_native`.
- `makeWrapper` around the binary:
  - `LD_LIBRARY_PATH` gets the libs that the Rust bindings `dlopen` instead of
    linking: **libglvnd** (the `libGL.so.1`/`libEGL.so.1` dispatchers), Wayland,
    X11, xkbcommon, fontconfig, ALSA — plus `/run/opengl-driver/lib`, NixOS's
    OpenGL driver directory. Mesa is deliberately **not** on the path: in nixpkgs
    it only ships the vendor ICD, and a second mesa next to the system driver
    breaks context creation (see Troubleshooting).
  - `PATH` gets `ffmpeg`/`ffprobe` (in-app video playback shells out to them) and
    `xdg-open` (the `open` crate).
- `meta.mainProgram = "artcraft"`, so `nix run` and `lib.getExe` hit the wrapper.
  Both `artcraft` and `artcraft-native` exist in `$out/bin`.
- Release profile gets `LTO = "thin"` and `codegenunits = 16`; a full `lto = true`
  build costs several minutes for little gain on a GUI app.

## Caveats

**Craft apps (prebuilt):**

- **Store size.** Each app's closure is ~375 MB (150 MB upstream ELFs plus the
  `xdg-utils` chain: perl, file, shared-mime-info, glib). Thirteen products make
  `.#craft-suite` gigabyte-scale, so it is opt-in and `nix build .` still
  defaults to the ArtCraft source build.
- **Provenance.** `sourceProvenance = binaryNativeCode`: no rebuild from source,
  hashes come from the same GitHub release as the binary (GitHub TLS, unsigned
  artefacts, no cosign/Sigstore/attestation published). We record upstream's
  `SHA256SUMS.txt` line verbatim in `pins.lock.json` so a swap is visible in a
  diff.
- **Runtime verification.** photocraft (Wayland + XWayland), soundcraft (ALSA
  device opens), filmcraft (VA-API/NVDEC absent → falls back to software decode)
  and pdfcraft (wgpu on the Vulkan RADV adapter) were launched here; all twelve
  pass the headless `<app>-cli --version` check and their upstream `.desktop`
  files pass `desktop-file-validate` untouched. The remaining eight are
  build-and-CLI verified, not GUI-verified — they are the same codebase family,
  so a wrapper bug in one is likely a wrapper bug in all, and the audit flags are
  per-product rather than shared.
- **Portals.** Without `xdg.portal.enable = true` (plus a portal implementation)
  Open/Save dialogs and the colour picker fail: every product embeds an rfd
  `xdg-desktop-portal` client and needs `libdbus-1.so.3` (the wrapper provides
  it) and a running portal.
- **Hardware video decode (filmcraft).** It dlopens `libva.so.2`/`libva-drm.so.2`
  (and `libnvcuvid.so.1`/`libnvidia-encode.so.1`). Those must come from your
  system, not the store — put `libva` and the VA-API driver in
  `hardware.graphics.extraPackages` so they appear in `/run/opengl-driver/lib`.
  Without them FilmCraft logs "no VA-API hardware decoding" and works.
- **Theme detection** shells out to `/usr/bin/gsettings`, which does not exist on
  NixOS; the app reads `org.freedesktop.portal.Settings` first. Dark/light
  behaviour without either is a P2 item.

**ArtCraft (source build):**

- **`aarch64-linux` is unevaluated here.** `cargo vendor` pulls every target in
  `Cargo.lock` (we saw `windows-sys`, `wit-component`, ... in the vendor log), so
  `cargoHash` is host-independent in practice — but if `nix build .#artcraft`
  on aarch64 reports a different hash, run `nix run .#update-pins` there and
  compare.
- **First build is heavy.** Vendoring the workspace lockfile (Tauri, `sqlx`,
  `wreq` and other crates this build never compiles) is a few hundred MB.
- **Wayland decorations**: the app draws its own title bar
  (`with_decorations(false)`), so it behaves like a client-side-decorated window.
  Verified under niri (Wayland) and through XWayland on an AMD Navi 48 (RX 9070) + Granite Ridge iGPU box, against the system mesa 25.0.7 driver.
- **GPU driver comes from your config.** This flake ships the GL *dispatchers*
  only; the actual driver must exist on the system (`hardware.graphics` +
  `enableDrivers` on NixOS, or the distro's mesa/nvidia packages elsewhere).
- The app is a network client: it does nothing useful without an ArtCraft
  account/API access.

## Troubleshooting

**Craft apps: the "missing libraries … start anyway" dialog**

Each app runs its own preflight over the sonames listed above (with
`LD_LIBRARY_PATH` and `ldconfig -p` as the two ways to satisfy it; NixOS has
neither an `ld.so` cache nor `/sbin/ldconfig`, so the wrapper's
`LD_LIBRARY_PATH` *is* the spec). If you see that dialog, the wrapper list is
wrong, not your system — and `PHOTOCRAFT_SKIP_LIB_CHECK=1` exists upstream as an
escape hatch we deliberately do **not** set, because needing it would hide a real
regression. `nix build .#photocraft && grep LD_LIBRARY_PATH result/bin/photocraft`
should list libglvnd, vulkan-loader, wayland, libx11, libxkbcommon, dbus.

**Craft apps: Vulkan/GL init failures**

The closure carries the *dispatchers* (`libvulkan.so.1`, `libEGL.so.1`,
`libGL.so.1`) and `/run/opengl-driver/lib`; the actual driver comes from the
system (`hardware.graphics.enable` + `enableDrivers` on NixOS). A
`radv is not a conformant Vulkan implementation` warning is upstream mesa talking,
not a packaging bug. `--safe-gpu` starts the app on the CPU renderer; the
`WGPU_BACKEND` env var overrides the backend (e.g. `WGPU_BACKEND=vulkan`).

**ArtCraft: `NoGlutinConfigs`**

glutin `dlopen`s `libEGL.so.1` / `libGL.so.1` at runtime. In nixpkgs those
*dispatchers* only exist in `libglvnd` — `mesa` ships just the vendor libs
(`libEGL_mesa.so.0`, `libGLX_mesa.so.0`) — so a package whose
`LD_LIBRARY_PATH` has mesa but not libglvnd finds no GL implementation and dies
exactly like this. Verified on this machine:

| `LD_LIBRARY_PATH` | result |
|---|---|
| nixpkgs `mesa` + X11/Wayland libs (the original wrapper) | **NoGlutinConfigs** |
| `libglvnd` + X11/Wayland libs | renders (Wayland and XWayland) |
| `libglvnd` + `/run/opengl-driver/lib` | renders |

The derivation now uses the libglvnd row, so if you still see this error:

1. You are running a stale build — `nix build .#artcraft` and check
   `grep libglvnd result/bin/artcraft-native`. Before the fix the wrapper listed
   `...-mesa-.../lib` instead.
2. No system OpenGL driver: the wrapper supplies dispatchers only. On NixOS that
   means `hardware.graphics.enable = true` (plus
   `services.xserver.videoDrivers = [ "nvidia" ];` on NVIDIA) so
   `/run/opengl-driver/lib` and
   `/run/opengl-driver/share/glvnd/egl_vendor.d/*.json` exist; elsewhere the
   distro's mesa/nvidia packages play that role.
3. Version skew between this flake's nixpkgs and the system driver — debug with
   `LIBGL_DEBUG=verbose EGL_LOG_LEVEL=debug artcraft`.

To separate driver problems from packaging problems, try software rendering (it
still needs a working system mesa, but no kernel-mode GPU driver):

```bash
LIBGL_ALWAYS_SOFTWARE=1 GALLIUM_DRIVER=llvmpipe nix run .#artcraft
```

If your session looks fine but the app cannot connect to Wayland
(`NoWaylandLib`), it did not find `libwayland-client.so.0`; the wrapper provides
it, so that symptom means something stripped `LD_LIBRARY_PATH` (e.g. running the
unwrapped `bin/.artcraft-native-wrapped` directly). Always start
`bin/artcraft` (or `bin/artcraft-native`).

## Packaging the Tauri app instead

If you need the full official app (all pages, 3D scene tools), build
`crates/desktop/artcraft`: `buildNpmPackage`/`npmBuild` for `frontend/`, then
`rustPlatform.buildRustPackage` with `cargoBuildFlags = [ "--package" "artcraft" ]`,
`webkit2gtk_4_1`, `wrapGAppsHook3`, `cargo-tauri` and the `dist` folder the
Tauri config expects. Upstream's entry point is
`./script/artcraft/unix_dev.sh` (dev) and `_docs/dev_setup.md`.

## Wrapping the macOS app (not implemented)

macOS hosts can skip compiling: `fetchurl` the release asset
(`ArtCraft_<ver>_universal.app.tar.gz` or `..._universal.dmg`) with its
`sha256`, unpack it in a fixed-output derivation, move `ArtCraft.app` into
`$out/Applications`, and gate the package on `stdenv.hostPlatform.isDarwin`.
Since the bundle is already signed and notarised upstream, don't re-sign it; the
usual Gatekeeper/quarantine caveats apply to any download.
